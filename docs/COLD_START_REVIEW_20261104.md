# 冷唤醒首音与生命周期检查

## 已确认并修正的路径

- `.41` 的音频组件在 engine/player 启动后就读入并播放 PCM，主程序随后才在异步 READY 回调中按下 Fn。音频引擎就绪不等于微信已经收音。`.42` 将启动 PCM 保留在内存中，组件 READY 后先按 Fn，沿用 VibeStick 的 350ms 唤起间隔，再顺序送出前缀并进入实时流。移除 audio-only 组件中位于 Fn 之前的多余350ms等待。
- 实际管道实验确认 `readData(ofLength:16000)` 会等待读满，导致16kHz/Int16流攒约半秒才处理。改为640字节，即20ms一块。实际 audio-only 组件只收到一帧合成静音、stdin仍打开时，0.1ms内已排入播放；此指标是调度延迟，不是微信浮窗或识别延迟。
- 目标F7可能先于IOHID匹配回调到达；原接收循环取出后因未独占而丢弃。现在未独占时不取走目标队列，待独占成功后再交付。队列仍只接收经目标地址/连接/CID/方向检查的F7，64帧上限保持，断连清空，不扩大监听设备范围。
- 组件启动或Fn预热期间已经松开时，先送完缓冲再关闭stdin，避免短句全部丢失；显式取消则丢弃未播放前缀、关闭stdin、释放Fn和恢复麦克风。
- 启动五秒未完成会关闭组件输入并恢复现场；启动及等待下一句的PCM缓存上限各为五秒，超过后报告错误并恢复，不无限增长。就绪消息只处理一次，旧组件延迟回调按进程身份拒绝。

## 自动检查

应用自测覆盖：READY前/预热期间的样本顺序、重复READY、预热前结束的短句、一次性排空、转入实时流、缓存满拒绝。Release构建和应用自测通过。原生后端ASan/UBSan生命周期回归通过。实际BlackHole audio-only静音测试不触发Fn、不采集麦克风，确认20ms块在EOF前调度且正常排空退出。

## 尚未消除的边界

- 遥控器建立无线连接之前没有发送给Mac的声音，主机无法补回。当前没有物理按键瞬间的独立时间戳，不能把用户按下到蓝牙连接完成的延迟归因于应用，也不能承诺瞬间收音。
- Fn等待350ms来自既有组件行为，没有微信提供的“已开始收音”API确认，仍须实物冷唤醒核对首词；不能只凭离线缓存测试宣布不再缺字。
- 目标原生队列64帧约1.28秒，独占迟迟不成立仍可能溢出并记录dropped；不会绕过独占直接送音。
